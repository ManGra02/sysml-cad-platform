1. Introduction
1.1 Purpose
<Identify the product whose software requirements are specified in this document, including the revision or release number. Describe the scope of the product that is covered by this SRS, particularly if this SRS describes only part of the system or a single subsystem.>

This document specifies the software requirements for the Bi-Directional Synchronization system (BDS) between a SysML v2 and a CAD model. It will be a subsystem in a system engineering assistant suite.
The scope covered by this document is the synchronization layer itself: the access to both models, the mapping model that connects them, the verification, change-impact and reporting functions built on top of that mapping. Also the user interface through which engineers operate the system is described. The SysML v2 repository, the CAD kernel and the AI service are existing third-party components that are not specified here.

1.3 Product Scope
<Provide a short description of the software being specified and its purpose, including relevant benefits, objectives, and goals. Relate the software to corporate goals or business strategies. If a separate vision and scope document is available, refer to it rather than duplicating its contents here.>
Bi-Directional Synchronization (BDS) maintains data consistency between the logical SysML v2 architecture and the physical 3D CAD model. It provides three capabilities:
    • parameter propagation, that is updating the system model with computed mechanical properties from the CAD environment such as material and size
    • constraint verification, that is evaluating CAD-derived parameters against defined system boundaries
    • and impact traceability, that is correlating requirement modifications with the affected geometric entities.
The problem addressed is a document-based working practice. Today, target values live in the system model while actual values live in the CAD model, and the comparison between them is done by hand. Deviations therefore become visible long after they were introduced. BDS replaces this with a model-based practice: limits are stored in the system model as machine-checkable rules, actual values are pulled from the CAD model automatically, and deviations surface immediately.
The intended benefits are the following. Budget overruns in mass or installation space are detected instant. Unilateral changes to agreed interface dimensions become visible across subsystem boundaries when several design owners work in parallel. The consequences of a design change are derived from the model instead of being estimated by an engineer. Verification results are captured directly as review and certification evidence, which removes the manual compilation of documentation.

5.1.1 FREQ-1: Access to the system model
The system shall connect to a SysML v2 repository through the standard Systems Modeling API and Services and read the elements of a selected project and commit.

Description: The user configures the endpoint, the project and the branch. The system retrieves the part definitions and usages, the attribute usages and the requirement and constraint definitions of the selected commit, and holds them in an internal read-only working copy for the duration of the run. The identifier of the commit is recorded, so that every later result can be attributed to an exact state of the system model. Read access to the system model is a precondition for every other function of the product.
User Priority(x/5): 5/5
Technical Priority(y/5): 5/5

5.1.2 FREQ-2: Access to the CAD model
The system shall access the currently opened CAD document and read its assembly structure, its named parameters and its geometry-derived properties.

Description: The system reads the object tree, the named parameters maintained in skeleton objects and spreadsheets, and the computed properties volume, mass, bounding box, centre of mass and assigned material. Reading does not modify the document and does not hold it in a state that prevents the design engineer from continuing to work. Where a property cannot be computed, for example because a part has no material assigned, the system reports the gap instead of substituting a value.
User Priority(x/5): 5/5
Technical Priority(y/5): 5/5

5.1.3 FREQ-3: Mapping model
The system shall maintain an explicit and persistent mapping between elements and attributes of the system model and objects and parameters of the CAD model.

Description: A mapping entry consists of the identifier of the system model element and the name of its attribute, the CAD object and its parameter, the unit on each side together with the conversion between them, the synchronization direction (target value downwards, actual value upwards, or both), an optional tolerance, and a status of proposed, confirmed or disabled. The mapping is stored with the project in a human-readable format and can be placed under version control. The mapping is what makes the behaviour of the system predictable: it, and not the AI component, decides which value is compared against which.
User Priority(x/5): 4/5
Technical Priority(y/5): 5/5

5.1.4 FREQ-4: AI-assisted mapping proposal
The system should propose candidate mappings between the system model and the CAD model using an AI service.

Description: On request, the system passes a structural excerpt of both models to the AI service, which returns candidate correspondences following the pattern shown in Appendix B: part definitions correspond to component definitions, interfaces and connections correspond to assembly constraints, and attributes correspond to parameters. Each candidate carries a confidence value and a short rationale. Candidates are never applied automatically; they enter the mapping table with the status proposed. Establishing the mapping by hand is the most tedious step of setting up the system, which is why this support is worth having even though it is not strictly necessary.
User Priority(x/5): 4/5
Technical Priority(y/5): 3/5

5.1.5 FREQ-5: Confirmation of mappings
The system shall require explicit human confirmation of a mapping entry before that entry is used in any synchronization or verification run.

Description: The user reviews a proposed entry, adjusts units, direction and tolerance where necessary, and then confirms or rejects it. The confirmation is recorded with the user and the timestamp. This requirement is what allows an AI component to be used at all without giving up reproducibility: after confirmation, the entry is an ordinary deterministic rule and its origin no longer influences the result.
User Priority(x/5): 4/5
Technical Priority(y/5): 5/5

5.1.6 FREQ-6: Structural instantiation
The system shall generate and update a CAD skeleton structure derived from the part structure of the system model.

Description: For every part usage in the selected branch of the system model, a corresponding node is created in the CAD assembly if none is mapped yet, preserving the hierarchy and the naming of the system model. Existing objects are identified through the mapping and are never replaced. Objects created by the system are marked as generated, so that a later run can tell them apart from objects the design engineer created manually and can update them without touching the manual work.
User Priority(x/5): 4/5
Technical Priority(y/5): 4/5


5.1.7 FREQ-7: Automated target–actual verification

The system shall evaluate the extracted actual values against the limits, budgets and agreed values defined in the system model, and shall report a verdict for every evaluated constraint.

Description: This is the central function of the product. Every constraint yields one of three verdicts – compliant, within tolerance, or violated – together with the actual value, the target value and the deviation. The same mechanism covers all four operational cases identified in the concept: budget tracking, where mass and installation space are checked against the allocations of the subsystems; interface control, where agreed interface dimensions are compared against the as-designed geometry across subsystem boundaries; replacement part approval, where a substitute material or an alternative component is checked against the original requirements; and substance compliance, where regulatory thresholds and recycling ratios stored as requirements are checked against the material and mass data of the CAD model. The four differ only in which constraints are evaluated and in what triggers the run, not in the evaluation logic. The evaluation is deterministic and its result depends only on the two model states and the mapping.
User Priority(x/5): 5/5
Technical Priority(y/5): 5/5

5.1.8 FREQ-7: Change impact analysis
The system shall determine, for a given change in either model, which elements of the other model, which requirements and which verification cases are affected.

Description: The analysis follows the mapping entries and the traceability links of the system model, and returns the affected requirements and verification cases together with the link path that led to each of them. The example from the concept illustrates the value: switching a housing from aluminium to plastic looks like a local design change, but it affects the mass budget, the thermal path and the material certification. The system derives this from the links instead of leaving the estimate to the engineer. Results that follow from an incomplete link structure are marked as such, because the analysis can only be as complete as the model it traverses.
User Priority(x/5): 5/5
Technical Priority(y/5): 4/5

6.2.3 SCN-2: Detect a unilateral interface change

FREQ reference	-
NFREQ reference	-
Short Description:	A designer changes a mounting dimension without coordinating it. The next check compares as-designed geometry against the agreed interface definition and reports the exact deviation.
Activation action:	A CAD change event, or the scheduled check run.
Precondition:	The interface dimensions are agreed and stored in the system model. The change is not applied in both models (due to multiple engineers working in parallel or sync is forgotten).


Basic flow: Detect a unilateral interface change
Step	User action	System response
1	Designer A saves a changed mounting dimension in CAD.
2		Detects the change and reads the affected interface parameters.
3		Compares them against the agreed interface definition and finds a deviation.
4		Shows agreed value, as-designed value and who changed it.
5	Engineer(s) agree on resolution and fix the derivation in SysMLv2 or CAD model (or both).
6		Re-runs the check and closes the finding when it passes.
Post-condition:	The deviation is resolved and the check has run successfully.
